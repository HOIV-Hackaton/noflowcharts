# Technical Report

## Goal

This project implements a human-controlled AI service desk workspace for the techbold Phoenix ERP challenge. The application loads assigned tickets, retrieves customer SSH targets, proposes one safe troubleshooting command at a time, records an audit trail, validates recovery, and submits complete activity documentation back to Phoenix.

## Architecture

The backend owns all privileged operations and secrets. Phoenix tokens, SSH keys, SSH execution, LLM calls, safety checks, audit logging, and activity submission never move to the browser.

Key backend modules:

- `clients/phoenix.py`: Phoenix ERP client with bearer auth, timeouts, retries, and sanitized errors.
- `services/ssh_runner.py`: single-command SSH executor with bounded output and timeout reporting.
- `services/safety.py`: command classification and hard-fail blocking for dangerous operations.
- `agent/planner.py`: Azure OpenAI-backed planner that returns exactly one proposed command.
- `services/run_manager.py`: run state machine enforcing SSH confirmation, per-command approval, risky typed confirmation, validation confirmation, and activity submission guards.
- `services/activity_generator.py`: Azure OpenAI-backed draft generator for required Phoenix/scoring fields.
- `services/audit_log.py`: append-only audit events with redacted payloads.
- `db/` and `repositories/`: SQLite persistence for runs, actions, command results, activity drafts, audit events, and WebSocket replay.

The React/Vite frontend remains the starter scaffold in this branch. The backend exposes the REST and WebSocket surfaces needed to wire ticket filters, customer system details, run controls, approval/edit/reject/retry/abort controls, logs, validation confirmation, and activity review/submission.

## Safety Controls

- SSH connection must be explicitly confirmed before system actions.
- Every command requires technician approval before execution.
- Risky commands, including `sudo`, require typed confirmation.
- Edited commands are reclassified before execution.
- Blocked commands cannot be approved or executed.
- Activity submission requires validation evidence and explicit human review.
- Phoenix ticket status changes to `DONE` only after activity creation succeeds.
- Secrets and likely credentials are redacted from audit payloads and LLM prompts.

## Activity Documentation

The submitted Phoenix activity includes all scoring fields: `summary`, `root_cause`, `actions_taken`, `commands_summary`, and `validation_result`, plus `description` for the OpenAPI response shape. The activity draft can be generated by Azure OpenAI and then edited before review and submission.

## Reproducibility

Configure `.env` from `.env.example`, place the private key under `keys/`, then run with Docker Compose or local backend/frontend commands from the README.

Recommended checks:

```bash
cd backend && .venv/bin/pytest
cd frontend && npm run build
```

## Known Limitations

- Active command execution is not resumed after backend restart.
- The troubleshooting loop depends on configured Azure OpenAI credentials for new command proposals and draft generation.
- The frontend still needs to be wired to the stabilized backend APIs.
